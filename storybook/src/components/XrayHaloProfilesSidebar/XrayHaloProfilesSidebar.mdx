# XrayHaloProfilesSidebar

X-ray Halo Profiles' real per-tile sidebar — the simplest in this app. `app.py`'s own `elif statistic == "X-ray Halo Profiles":` render block (no matching sidebar-params block at all) confirms this statistic has no dedicated controls beyond Suite/Set/Realization.

## Token

Composed entirely from `SingleRealizationFields`/`Button` — no tokens of its own.

## Spec

<Canvas of={XrayHaloProfilesSidebarStories.Playground} />
<Controls />

- Suite/Set/Realization: `SingleRealizationFields` — one of `app.py`'s own `SINGLE_REALIZATION_STATISTICS`, so no Compare mode.
- Set now includes real `1P`/`EX` alongside `LH`/`CV` (2026-08-08, issue #51) via `allowedSetsForSuite` — IllustrisTNG gets all four; SIMBA gets `LH`/`CV`/`1P` only, since its own real collated file has zero `EX` entries (confirmed via a direct listing, not a fetch gap).
- `onepScheme="flat"` — this product's real `1P` data is a bare `1P_{N}` flat index (0–65) in the underlying file, not the param+variation folder naming other 1P-aware statistics use, and with no independently-confirmed mapping back to a specific parameter/variation. Rather than guess a split, `SingleRealizationFields` shows it as a plain Realization number with a caption disclosing the caveat.
- No other fields. Not a placeholder — `app.py` genuinely has none for this statistic.

## Usecase

- Real usage: `App.tsx`'s canvas — `onChange` triggers a real refetch of `GET /api/xray-profiles` (JSON) and `/plot.png` (the real render — see `StaticImageChart.mdx`, `PlotTile`'s `chart.kind: 'static-image'`).
- **Real-data only, no synthetic fallback** — `get_xray_profiles()` returns `None` outright for suites without this product. Only **IllustrisTNG and SIMBA** (real, per `backend.py`'s own docstring), and only the single published snapshot (`snap_032`, z=0.05) — there is no Snapshot control here because there is nothing real to control.
- No halos table under this tile in the `UnderlyingHalos` sense — the chart itself already shows every halo in the realization (one line each, colored by mass); a second, separate per-subhalo Subfind table would be redundant with what the chart already displays. See `UnderlyingHalos.mdx`.
