# DensityFieldChart

3D Density Field's real chart, from `app.py`'s own `elif statistic == "3D Density Field":` block — a `go.Volume` trace built from the exact same meshgrid + isomin/isomax-by-percentile recipe, plus a real optional VIDE void overlay.

## Token

Composed from `Plotly3DChart` — no tokens of its own. Colors are real, not app tokens: `INFERNO_COLORSCALE` and the void overlay's `cyan`/`lightcyan` markers.

**Real bug fixed 2026-08-05: `colorscale: "Inferno"` (the literal string) doesn't actually render Inferno in this app.** Direct user report that the colors looked visibly worse than `app.py`'s real Streamlit rendering, despite the code passing the identical-looking string `app.py` uses. Root cause, confirmed empirically (rendered a `colorscale: 'Inferno'` heatmap and read back `gd._fullData[0].colorscale`): `plotly.js-dist-min`'s named-colorscale registry stores this palette under a lowercase key (`inferno`) — the capitalized string `"Inferno"` the public API/Python convention uses doesn't match it and silently resolves to a *different* built-in scale (a pale-grey-to-red gradient), not an error and not the real Inferno either. Fixed by reading `plotly.colors.sequential.Inferno` directly from the installed Python package and hardcoding its real 10 hex stops as an explicit `[[position, color], ...]` array (`INFERNO_COLORSCALE`) instead of the string — this is the literal palette Streamlit renders, not an approximation, and sidesteps the naming mismatch entirely.

**Real root cause found 2026-08-07: `surface_count` (flat key) never actually applied — the render silently had exactly 2 isosurface shells, not 12.** `surface_count` is a `plotly.py`-only "magic underscore" convenience that Python expands into `{"surface": {"count": ...}}` before a figure is ever serialized — `plotly.js` has no such expansion (confirmed against its own installed schema and shipped bundle: no `surface_count` key exists anywhere in it, only nested `surface.count`, defaulting to 2). So this trace was rendering isomin's shell (near-black on Inferno, invisible at low opacity) and isomax's shell (the sparse, mutually disconnected top-0.5%-density halo cores) only — regardless of the sidebar's own Iso-surfaces value. `app.py`'s identical `surface_count=iso_surfaces` kwarg genuinely produces the real nested shells server-side, which is what reads as one continuous, alpha-composited structure. Fixed by setting `surface: { count: isoSurfaces }` (the properly nested key) instead of the flat `surface_count`.

**Investigated and ruled out 2026-08-07, direct user report ("the legend ends with black for 5 and below, Streamlit's ends with red"): the colorbar/legend itself is correct here, not a bug in this app.** Reproduced Streamlit's real `3D Density Field` colorbar directly (ran `app.py` locally, inspected the live `_fullData[0].colorscale` the same way as this component's own render) and found its first stop resolves to `#ffabab` (a salmon-pink) instead of Inferno's real near-black `#000004` — even when the *literal, correct* 10-stop array is passed straight into `go.Volume(colorscale=...)` from Python, bypassing any string-name resolution entirely. Isolated further in a minimal from-scratch Streamlit script (no CAMELS code at all): `Viridis`/`Reds`/`Portland` all render their correct first stop in the same environment, only `Inferno`'s does not — a real, reproducible rendering bug specific to the exact `plotly.js` version Streamlit bundles (`window.Plotly.version` reads `3.1.0` there, vs. this app's own `3.7.0`, confirmed bug-free for this exact case via the same `_fullData[0].colorscale` check). This app's own colorbar was cross-checked against Python's own `plotly.colors.sequential.Inferno` and `go.Volume(...).to_plotly_json()['colorscale']` for the identical real dataset and matches stop-for-stop, including the correct near-black bottom — i.e. this app's legend is the accurate one; Streamlit's is the one showing an artifact. Not "fixed" here since there's nothing wrong on this side to fix.

## Spec

- Builds `x`/`y`/`z`/`value` flat arrays from the real `(grid, grid, grid)` density array and `box_size`, matching `app.py`'s own `np.meshgrid(coords, coords, coords, indexing="ij")` exactly (coordinates run `0` to `box_size` in `grid` steps). `value` is the literal density array — linear, not log-transformed (see the reverted attempt below).
- `isomin`/`isomax` are the real 60th/99.5th percentile of the value array — same real percentile thresholds `app.py` uses (`np.percentile(vals, 60)`/`np.percentile(vals, 99.5)`), not arbitrary round numbers.
- `colorbar.title` is `"ρ/ρ̄"` for the four mass-type fields (Mtot/Mgas/Mcdm/Mstar) or the raw field name otherwise — matches `app.py`'s own `colorbar_title` conditional.

**Tried and reverted 2026-08-05: log10-transforming `value`.** Direct user report the render looked wrong ("majority black, olive green gases") led to trying the same `log10` fix the 2D Field Map applies via `LogNorm` (a real cosmological field spans several orders of magnitude, and mapping that linearly does put most typical-density cells low in the color range). Shipped it; direct user report afterward was that it made the render *worse*. A side-by-side Figma comparison against `app.py`'s real Streamlit output — same suite/set/realization/field, and critically the same **Snapshot** value once that was tracked down as the missing variable — confirmed identical `isomin`/`isomax` between the two apps, ruling out a data mismatch. The real mechanism, precisely quantified against that data: with `surface_count` fixed at 12, **linear** spacing between isomin/isomax spends only 1 of those 12 levels on the high-coverage "boring" bulk (>13% of the box) and the other 11 resolving the sparse, interesting tail (13%→0.5% coverage) where real cosmic-web structure lives; **log** spacing spreads levels evenly in log-space instead, which for this same data spent 7 of 12 levels on that same bulk and only 5 resolving the tail — starving the interesting structure of resolution. `app.py`'s literal linear approach isn't naive, it's well-suited to a heavy-tailed distribution's percentile-bounded isosurface budget. Reverted to the literal linear value/isomin/isomax.
- **Process note**: the first several attempts to diagnose this were validated only against headless-Chromium screenshots (SwiftShader software WebGL), which cannot be trusted for this component — see the reverted `opacityscale` attempt in git history for the other dead end that approach produced. The fix that actually held up was found by comparing real numbers (backend percentiles, colorbar tick values) against a real user-provided screenshot of the actual Streamlit output, not by rendering more screenshots of our own.
- **Real bug fixed 2026-08-05, unrelated to the above: colorbar tick/title text was illegible.** Plotly's own default colorbar font color (`rgb(68,68,68)` ticks, pure black title) assumes a light page background — invisible against this app's dark chrome. Fixed with explicit `tickfont`/`title.font` colors matching `Plotly3DChart`'s own `AXIS_TEXT_COLOR` literal.

- **Void overlay** (`voids` prop): a second `go.Scatter3d` trace, cyan markers sized by real radius (`Math.min(40, Math.max(6, r * 3))`, matching `app.py`'s own `np.clip(voids.radius * 3, 6, 40)`), real hover text built from `voids.extra`'s real columns (`void_id`, `num_part`, `vol`, `tree_level`, `n_children`) when present, or just radius/density-contrast otherwise — matches `app.py`'s own two-branch hover-text f-string exactly.
- **Built 2026-08-07 (direct user request), after being deliberately deferred here**: `app.py` also shows the void catalog as its own real, downloadable table (`st.dataframe` + CSV export) in an expander below the chart when voids are shown. Rather than fork a second table component, `UnderlyingHalos` itself was generalized (columns/wording/filter all now overridable, defaulting to the original per-halo behavior) and this statistic's void data feeds it via `PlotTile`'s new `catalogTable` prop — a "Table" `ChartModeDropdown` option, not a section under the chart, matching every other statistic's own table pattern (see `PlotTile.mdx`/`UnderlyingHalos.mdx`).

## Usecase

- Real usage: `App.tsx`'s canvas, via `PlotTile`'s `chart.kind: 'plotly-3d'` — fed real data from `GET /api/density-field-3d` (and `GET /api/void-catalog` when the "Overlay VIDE void catalog" checkbox is on).
- Always has a value (real CMD grid, real raw-snapshot gridding, or a synthetic lognormal-field fallback) — `get_density_field_3d()` never returns `None`.
- Performance note, matching `app.py`'s own real help text ("Higher = finer structure but slower to rotate"): building the flat `x`/`y`/`z`/`value` arrays is a real `O(grid³)` operation in JS — the default grid (32³) is fast; the max (128³, ~2M points) is real and works, just slower, the same real tradeoff Streamlit's own slider warns about.

## Code

```tsx
import { DensityFieldChart } from '@/components/DensityFieldChart/DensityFieldChart';

function DensityFieldTile({ result, isoSurfaces, opacity, voids }) {
  return (
    <DensityFieldChart
      density={result.density}
      boxSize={result.box_size}
      colorbarTitle="ρ/ρ̄"
      isoSurfaces={isoSurfaces}
      opacity={opacity}
      voids={voids}
    />
  );
}
```
